# 개발기록

## 문서 목적

본 문서는 `university-cms-php` 프로젝트를 진행하면서 작성한 개발기록입니다.

단순 작업 내역뿐 아니라 요구사항 정리, DB 설계, 화면 구성, 테이블명 결정, 구현 범위 조정 등 프로젝트 진행 중의 판단 근거를 함께 기록합니다.

이 기록은 프로젝트를 처음부터 끝까지 구축하는 과정을 남기기 위한 문서이며, 실제 구현 과정에 따라 내용은 계속 추가될 수 있습니다.

## 2026-06-07

### 1. GitHub 저장소 생성

`university-cms-php` 저장소를 생성했습니다.

이 프로젝트는 대학교·공공기관 부속 홈페이지 운영을 가정한 PHP·MySQL 기반 통합관리 CMS 개인 프로젝트입니다.

저장소명에는 프로젝트의 목적과 기술 스택이 드러나도록 `university`, `cms`, `php`를 포함했습니다.

### 2. README 작성

README에 프로젝트 개요, 개발 목적, 구현 예정 기능, 기술 스택, 문서 링크, 개발 진행 계획, 주의사항을 정리했습니다.

아직 기능 구현 전 단계이므로 완성된 기능처럼 보이지 않도록 `주요 기능`이 아니라 `구현 예정 기능`으로 표현했습니다.

웹에이전시/SI 환경에서 자주 요구되는 홈페이지 구축·유지보수 흐름을 연습하는 프로젝트로 정리했습니다.

### 3. .gitignore 추가

`.gitignore` 파일을 추가해 GitHub에 올리지 않을 파일과 폴더를 정리했습니다.

주요 제외 대상은 다음과 같습니다.

* `.env`, `.env.local`: DB 접속 정보나 비밀번호 등 민감정보 보호
* `vendor/`, `node_modules/`: 외부 라이브러리 설치 폴더 제외
* `logs/`, `*.log`: 실행 중 생성되는 로그 파일 제외
* `uploads/`: 게시글 첨부파일, 배너 이미지 등 업로드 파일 제외
* `.vscode/`, `.idea/`: 개인 개발환경 설정 제외

초기 단계에서 `.gitignore`를 추가해 민감정보나 불필요한 파일이 커밋되는 것을 방지하고자 했습니다.

### 4. 요구사항정의서 작성

`docs/requirements.md` 파일을 작성했습니다.

요구사항정의서에서는 사용자 유형과 기능 요구사항을 정리했습니다.

사용자 유형은 다음과 같이 구분했습니다.

* 최고관리자
* 사이트관리자
* 콘텐츠관리자
* 일반 방문자

초기에는 `일반 사용자`라는 표현도 검토했지만, 관리자도 넓은 의미에서는 사용자에 포함될 수 있으므로 홈페이지를 조회하는 대상은 `일반 방문자`로 표현하는 것이 더 명확하다고 판단했습니다.

또한 `권한관리`라는 표현보다 현재 설계에서는 `역할관리`가 더 적합하다고 판단했습니다.
이번 1차 설계의 `roles`는 기능 단위 권한이 아니라 최고관리자, 사이트관리자, 콘텐츠관리자 같은 관리자 역할을 의미하기 때문입니다.

### 5. DB 설계 초안 작성

`docs/erd.md` 파일을 작성했습니다.

요구사항정의서 작성 후, CMS에서 필요한 핵심 데이터 구조를 먼저 파악하기 위해 DB 설계 초안을 작성했습니다.

이 프로젝트는 여러 부속 홈페이지를 하나의 관리자 시스템에서 관리하는 CMS이므로, 사이트, 메뉴, 페이지, 게시판, 게시글, 첨부파일, 관리자 역할, 담당 사이트 제한 같은 데이터 구조가 중요하다고 판단했습니다.

파일명은 관례적으로 `erd.md`를 유지하되, 문서 제목은 `DB 설계 초안`으로 정리했습니다.

`ERD`는 Entity-Relationship Diagram을 의미하므로 `ERD 다이어그램`이라는 표현은 중복될 수 있다고 판단했고, 다이어그램 섹션명은 `관계 요약 다이어그램`으로 정리했습니다.

### 6. 테이블명 정리

DB 설계 과정에서 헷갈릴 수 있는 테이블명을 정리했습니다.

#### users 대신 admins 사용

초기에는 로그인 계정 테이블명을 `users`로 생각했지만, 이 프로젝트에서는 일반 방문자가 로그인하지 않고 관리자만 로그인합니다.

따라서 로그인 계정 테이블명은 `users`보다 `admins`가 더 명확하다고 판단했습니다.

#### files 대신 post_files 사용

첨부파일 테이블도 처음에는 `files`로 생각했지만, 1차 개발에서는 첨부파일을 게시글에만 연결하기로 했습니다.

배너나 팝업 이미지까지 포함하는 공통 파일 테이블처럼 보이지 않도록 `post_files`로 명명했습니다.

#### board_type의 file 대신 resource 사용

게시판 유형에서 자료실을 `file`로 표현하면 `post_files`와 헷갈릴 수 있다고 판단했습니다.

그래서 자료실 게시판 유형은 `resource`로 표현하기로 했습니다.

### 7. 관계 요약 다이어그램 정리

Mermaid로 전체 테이블과 컬럼을 한 번에 표현했을 때 가독성이 떨어졌습니다.

그래서 컬럼 상세는 표로 정리하고, Mermaid 다이어그램은 관계를 이해하기 위한 요약 형태로 분리했습니다.

관계 요약 다이어그램은 다음 3개로 나누었습니다.

* 관리자 역할 및 사이트 담당 관계
* 사이트 콘텐츠 구조
* 이력 및 운영 로그 구조

이렇게 나누면 전체 구조를 한 번에 복잡하게 보여주는 것보다 각 영역의 관계를 이해하기 쉽다고 판단했습니다.

### 8. 화면목록 작성

`docs/screens.md` 파일을 작성했습니다.

일반적으로는 요구사항정의서 이후 화면목록을 먼저 작성하고 DB 설계를 진행할 수도 있지만, 이 프로젝트에서는 CMS의 데이터 구조가 중요하다고 판단해 DB 설계 초안을 먼저 작성했습니다.

이후 DB 설계 초안에서 정리한 `admins`, `sites`, `menus`, `pages`, `boards`, `posts`, `post_files`, `banners`, `popups`, `page_histories`, `admin_logs` 구조를 바탕으로 관리자 화면과 일반 방문자 화면을 정리했습니다.

관리자 화면에는 로그인, 대시보드, 사이트 관리, 메뉴 관리, 페이지 관리, 게시판 관리, 게시글 관리, 첨부파일 관리, 배너 관리, 팝업 관리, 페이지 수정 이력, 관리자 작업 로그 화면을 포함했습니다.

일반 방문자 화면에는 사이트 메인, 일반 페이지 조회, 게시판 목록, 게시글 상세, 첨부파일 다운로드 화면을 포함했습니다.

### 9. 현재까지의 설계 판단

현재 1차 개발 범위는 너무 넓어지지 않도록 다음과 같이 제한했습니다.

* 수정 이력은 우선 일반 페이지에 대해서만 관리한다.
* 첨부파일은 우선 게시글에 대해서만 관리한다.
* 팝업은 우선 텍스트 팝업 기준으로 설계한다.
* 배너와 팝업 이미지는 각 테이블에서 경로를 관리하고, 공통 파일 관리 구조는 향후 검토한다.
* 게시글 수정 이력, 롤백 기능, 기능 단위 세부 권한관리는 향후 검토 사항으로 둔다.

## 2026-06-08

### 1. Docker Compose 개발환경 구성

PHP·MySQL 기반 CMS 구현을 위해 Docker Compose 개발환경을 구성했습니다.

구성한 서비스는 다음과 같습니다.

* PHP 8.3 + Apache 앱 컨테이너
* MySQL 8.4 DB 컨테이너
* phpMyAdmin 개발 보조 도구

Apache의 웹 루트는 `public/`으로 설정해 `app/`, `database/`, `.env` 같은 내부 파일이 웹에서 직접 노출되지 않도록 했습니다.

또한 `public/.htaccess`와 Apache rewrite 설정을 추가해 `/admin/login`, `/admin/dashboard` 같은 관리자 URL을 `public/index.php`에서 처리할 수 있도록 했습니다.

### 2. DB 연결 구성

`app/Config/database.php` 파일을 작성해 `.env`의 DB 접속 정보를 읽고, PDO를 통해 MySQL에 연결하도록 구성했습니다.

DB 연결은 `db()` 함수로 재사용할 수 있게 했고, PDO 옵션으로 예외 기반 오류 처리, 연관배열 fetch, native prepared statement 사용을 설정했습니다.

### 3. 관리자 기본 테이블 및 seed 추가

관리자 로그인 구현을 위해 다음 테이블을 우선 생성했습니다.

* `admins`
* `roles`
* `admin_roles`

기본 역할로 `super_admin`, `site_admin`, `content_admin`을 추가했고, 개발용 기본 관리자 계정을 seed로 추가했습니다.

비밀번호는 평문 저장이 아니라 `password_hash()`로 생성한 해시값을 저장했습니다.

### 4. 관리자 로그인 화면 구현

`app/Views/admin/auth/login.php` 파일을 작성해 관리자 로그인 화면을 구현했습니다.

로그인 화면에는 다음 항목을 포함했습니다.

* 아이디 입력
* 비밀번호 입력
* 로그인 버튼
* 로그인 실패 메시지 출력
* 입력했던 아이디 유지

### 5. Admin 모델 구현

`app/Models/Admin.php` 파일을 작성해 관리자 조회 로직을 분리했습니다.

구현한 기능은 다음과 같습니다.

* username 기준 관리자 조회
* admin_id 기준 관리자 역할 목록 조회

로그인 처리에서 SQL을 직접 작성하지 않고, Admin 모델을 통해 관리자 정보를 조회하도록 구성했습니다.

### 6. 기본 관리자 로그인 처리 구현

`POST /admin/login` 요청을 처리해 실제 관리자 로그인이 가능하도록 구현했습니다.

처리 흐름은 다음과 같습니다.

1. 아이디와 비밀번호 입력값 확인
2. `admins` 테이블에서 관리자 조회
3. `password_verify()`로 비밀번호 검증
4. 활성 상태 관리자만 로그인 허용
5. 로그인 성공 시 세션에 관리자 정보 저장
6. 로그인 성공 후 `/admin/dashboard`로 이동
7. 로그인 실패 시 오류 메시지와 함께 `/admin/login`으로 이동

### 7. 관리자 로그아웃 구현

`/admin/logout` 라우트를 추가해 관리자 로그아웃을 구현했습니다.

로그아웃 시 세션 값을 비우고, 세션 쿠키를 만료시키며, 서버 세션을 종료한 뒤 로그인 화면으로 이동하도록 했습니다.

### 8. 관리자 세션 가드 분리

관리자 페이지 접근 시 반복되는 로그인 확인 코드를 `app/Core/Auth.php`로 분리했습니다.

추가한 함수는 다음과 같습니다.

* `isAdminLoggedIn()`
* `requireAdminLogin()`
* `currentAdmin()`

이를 통해 관리자 페이지에서는 `requireAdminLogin()` 호출만으로 로그인 여부를 확인할 수 있도록 했습니다.

### 9. 역할 기반 접근 제한 기초 구현

관리자 역할에 따라 접근을 제한할 수 있도록 `Auth.php`에 역할 확인 함수를 추가했습니다.

추가한 함수는 다음과 같습니다.

* `hasAdminRole()`
* `requireAdminRole()`

현재 `/admin/dashboard`는 `super_admin` 역할을 가진 관리자만 접근할 수 있도록 설정했습니다.

### 10. 다음 작업 계획

다음 구현 단계에서는 관리자 작업 로그 기능을 추가할 예정입니다.

우선 로그인, 로그아웃, 역할 제한 실패 같은 관리자 주요 동작을 기록할 수 있도록 `admin_logs` 테이블과 로그 저장 함수를 구현할 계획입니다.

## 2026-06-09

### 1. 관리자 작업 로그 테이블 추가

관리자 주요 동작을 추적하기 위해 `admin_logs` 테이블을 추가했습니다.

이번 단계에서는 관리자 작업 로그 기능을 너무 크게 만들지 않고, 먼저 로그 저장에 필요한 최소 구조를 구현했습니다.

`admin_logs` 테이블은 다음 정보를 저장하도록 구성했습니다.

* 관리자 ID
* 작업 유형
* 작업 대상 유형
* 작업 대상 ID
* IP 주소
* 작업 일시

로그인 실패의 경우 아직 로그인한 관리자를 특정할 수 없으므로 `admin_id`와 `target_id`는 `NULL`로 저장합니다.

### 2. AdminLog 모델 구현

관리자 작업 로그 저장 로직을 분리하기 위해 `app/Models/AdminLog.php` 파일을 추가했습니다.

`AdminLog::create()` 함수를 통해 로그인, 로그아웃, 역할 제한 실패 같은 관리자 주요 동작을 공통 방식으로 기록할 수 있도록 했습니다.

### 3. 관리자 로그인 성공 로그 기록

관리자가 정상적으로 로그인하면 `login` 로그를 기록하도록 구현했습니다.

이번 변경은 DB 구조나 메뉴 등록/수정 로직을 바꾸지 않고, 관리자 메뉴 목록 화면의 표시 방식만 개선한 작업입니다.

### 3. 현재 구현 범위 정리

현재 메뉴 관리는 사이트별 목록 조회, 등록, 수정, 상위 메뉴 선택, 상위 메뉴명 표시, 트리 들여쓰기 표시, 노출/숨김 처리까지 구현되었습니다.

관리자 작업 로그는 로그인 성공/실패, 로그아웃, 역할 제한 실패, 사이트 관리, 메뉴 관리 작업 기록에 더해 목록 조회 화면까지 구현되었습니다.

다음 단계에서는 문서 정리 후 일반 페이지 관리 또는 게시판 관리 기능으로 확장할 예정입니다.
